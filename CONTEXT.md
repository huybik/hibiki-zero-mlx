# Hibiki-Zero — local test project

Running Kyutai's **Hibiki-Zero** (simultaneous speech-to-speech + speech-to-text translation, FR/ES/PT/DE → EN) locally on an **Apple M4 Pro via MPS**. Upstream is NVIDIA-only; this project patches it to run on Mac.

- Model: `kyutai/hibiki-zero-3b-pytorch-bf16` (3B hierarchical transformer + Mimi codec @ 12.5 Hz). License CC BY-NC-SA 4.0.
- Repo/paper: https://github.com/kyutai-labs/hibiki-zero · https://arxiv.org/abs/2602.11072v1

## Layout (`/Volumes/data/models/hibiki-zero/`)
- `code/` — cloned inference repo (`hibiki_zero/run.py` = CLI, `inference.py` = core). Patched + installed editable.
- `code/main.py` — top entry point: `python main.py <audio>` (file → `translations/<stem>_translated.wav`, 3-thread fast path) or `python main.py --mic` (realtime mic → speakers, one encode→LM→decode worker per 80 ms frame; ~59 ms < budget so it keeps up). Both on q4 via `src/infer_mlx_fast`.
- `code/src/` — MLX library modules (`infer_mlx_fast.py` = pipelined inference `load()`/`run()`; `mlx_hibiki_patch.py` = stock-`moshi_mlx` shim). No packaging; scripts add `src/` to `sys.path`.
- `code/scripts/` — MLX entry points (`convert_mlx_*`, `convert_hibiki_m_mlx_q4`, `verify_mlx_q4`, `profile_mlx`, `push_*_q4`, `infer_mlx_bf16`, `exp_*`). Run from repo root, e.g. `python scripts/verify_mlx_q4.py`. Paths anchor on the repo root (`Path(__file__).resolve().parent.parent`).
- `code/moshi-mlx/` — **vendored fork of `moshi-mlx` 0.3.0** (git-tracked, installed editable from here). All hibiki-zero deltas are folded directly into it (see MLX section), so the project owns the MLX runtime and no longer depends on the PyPI package or a runtime monkey-patch.
- `code/weights/` — the checkpoint (gitignored): `config.json`, `hibiki-pytorch-77f82164@110.safetensors` (5.8 GB), `mimi-pytorch-e351c8d8@125.safetensors` (367 MB), `tokenizer_spm_48k_multi6_2.model`.
- `code/hibiki_zero/static/` — built Next.js frontend (from `build_frontend.sh`, needed by `serve`).
- `.venv/` — isolated venv (py3.13): hibiki-zero 0.0.4, moshi 0.2.13, moshi-mlx 0.3.0, torch 2.9.1. **Never** install into the conda base env.
- `code/translations/` — `generate` outputs (mono + stereo wav + txt), gitignored.
- `code/hibiki_zero/samples/` — bundled test clips: `leon.wav` (~64 s FR Olympics), `crepes.mp3`.

## MPS patches (in `code/`, why it runs on Mac)
1. `run.py`: CUDA guard → `if device == "cuda" and not torch.cuda.is_available()` (both `serve` and `generate`).
2. `inference.py`: `torch.cuda.synchronize()` wrapped in `if torch.cuda.is_available()`.
Installed with `pip install -e`, so edits stay live.

## Run
Batch translate a file (weights live in `code/weights/`):
```bash
cd /Volumes/data/models/hibiki-zero
./.venv/bin/hibiki-zero generate --device mps \
  --config-path code/weights/config.json \
  --model-weight "code/weights/hibiki-pytorch-77f82164@110.safetensors" \
  --mimi-weight "code/weights/mimi-pytorch-e351c8d8@125.safetensors" \
  --tokenizer code/weights/tokenizer_spm_48k_multi6_2.model \
  --file code/hibiki_zero/samples/leon.wav --gen-duration 66 --out-dir code/translations
```
Web UI (same flags, `serve` instead of `generate`): http://localhost:8998

## MLX 4-bit path (faster alternative to PyTorch/MPS)
Native MLX inference via the **vendored `moshi-mlx` fork** (`code/moshi-mlx/`). **~1.3× real-time** sequential (16.5 tok/s @ 12.5 Hz) vs ~0.7× for the bf16 MPS path; LM weights 5.8 GB → **2.2 GB** q4.
- **hibiki-zero deltas are folded into the fork** (stock pkg targets moshi/older-hibiki): (1) `lm.py:from_config_dict` honours `hidden_scale=6` + `kv_repeat=2` + depformer feedforward; (2) `transformer.py:Attention` does grouped-query attention; (3) same, wires `rope_concat` (RoPE interleave=False); (4) `lm.py:DepFormerSlice.norm` + `DepFormer.sample` + `load_pytorch_weights` add the learned per-slice depformer output **LayerNorm** (`depformer_norms.{i}`, applied before each audio `linear_out`) that stock moshi_mlx omits. **Without (4) the audio babbles** — overlapping/interleaved voices + clipping (depformer logits come out ~3× too small → out-of-distribution audio tokens); the text stream is unaffected since it never passes through the depformer. Diagnose with a silence-in test: feed zeros, a correct model stays near-silent (rms≈0.06, peak<1.0); the bug gives rms≈0.13, peak≈1.23 (clipping). **q4 weights must be regenerated** (`convert_mlx_q4.py`) after touching the depformer — the LayerNorm stays bf16 (nn.quantize skips non-Linear).
- `code/src/mlx_hibiki_patch.py` — the same four deltas as a **runtime monkey-patch of stock `moshi_mlx`**. The local fork-based scripts no longer import it; it is kept only as the portable shim published to HF for users on the PyPI `moshi-mlx` package.
- `code/scripts/convert_mlx_q4.py` — one-shot: load PyTorch LM → `nn.quantize(bits=4, group_size=32)` → `weights/hibiki.q4.safetensors`. Mimi codec stays separate/bf16.
- `code/scripts/verify_mlx_q4.py` — translates `leon.wav` via patched `moshi_mlx.run_inference` (uses `rustymimi` for the codec; our mimi sig `e351c8d8` loads directly). Output: `translations/leon_mlx_q4.wav`. Verified coherent FR→EN.
- Published q4 weights + patch + model card: [`huybik/hibiki-zero-3b-mlx-q4`](https://huggingface.co/huybik/hibiki-zero-3b-mlx-q4). **Keep `group_size=32`** — stock `moshi-mlx`/moshi-swift hardcode gs32 for `.q4.safetensors` (`run_inference.py:80`); gs64 saves ~240 MB but won't load without patching every loader (bad for the iOS/moshi-swift path).
- **Hibiki-M q4 staging:** `scripts/convert_hibiki_m_mlx_q4.py` downloads `kyutai/hibiki-1b-mlx-bf16@b3d6291...`, loads the MLX BF16 LM, quantizes group-size-32-compatible modules to q4, leaves tiny 16-dim conditioner tensors dense, patches `config.json` `moshi_name` to `hibiki-mlx-dc2cf5a5@80.q4.safetensors`, and stages a standalone repo at `weights/hibiki-m-mlx-q4/` (q4 LM 1.125 GB + Mimi + tokenizer + card). Published artifact: `huybik/hibiki-1b-mlx-q4@9649ed0ce90b1a93efac1a89a6bfbe44820c2e7b`. Vendored `moshi_mlx.models.lm` now handles Hibiki-M's float `hidden_scale=4.125` and optional depformer output LayerNorm; `run_inference.py` uses a group-compatible quantization predicate before strict q4 load.

## Speed work (in progress)
Profiled q4 decode (`code/scripts/profile_mlx.py`, per-stage w/ mx.eval barriers): mimi codec (rustymimi, **CPU**) was ~58%/frame (enc 30% + dec 28%), run *sequentially* with the GPU LM (main 20% + depformer 21%). rustymimi **releases the GIL**.
- `code/src/infer_mlx_fast.py` — overlaps codec with LM via 3 threads (encoder runs whole file ahead → queue → main-thread GPU LM step → decoder thread). Each thread needs its **own** `rustymimi.Tokenizer` (one instance borrowed by 2 threads → "Already borrowed" panic). FIFO queues keep streaming order ⇒ output byte-identical. **1.35× → 3.0× RT** (16.9 → 37.5 frames/s, 2.2×), zero quality change. Codec now hidden; GPU LM (~25 ms/frame) is the new floor. Reusable `load()`/`run()`.
- `code/scripts/verify_mlx_q4.py` — now wired to `infer_mlx_fast.run()` (the MLX entry point; ~2.8–3× RT). The PyTorch `serve`/`generate` in `run.py` are a **separate stack** (codec on MPS GPU, live-streaming) — this CPU/GPU-overlap trick doesn't apply there.
- `mx.compile` fast path (in the vendored `transformer.py:TransformerLayer`): single-token decode compiles `norm1+in_proj+reshape+RoPE` and `out_proj+residual+gated-FFN` as two fixed-shape graphs; the cache `update_and_fetch` + the one fused `sdpa` kernel stay eager between them (RoPE offset passed as a runtime array so a growing cache never recompiles). Byte-identical output. Toggle `MLX_LM_COMPILE=0`. **But only ~4%** (isolated LM 23.6 → 22.7 ms/frame; pipelined 3.01 → 3.11× RT) — the LM is **GPU-kernel-bound** on M4 Pro, not Python-dispatch-bound (MLX is already lazy; norms/RoPE/sdpa/FFN are already fused `mx.fast` kernels). So a full functional-cache / whole-step compile (the bigger rewrite) is unlikely to pay off; **pipelined 3× RT is near the practical floor** for this model on this hardware.
- **Bottleneck breakdown (fresh profile, M4 Pro):** per frame GPU LM ≈ 24 ms = main transformer 8.6 ms + **depformer 15.7 ms (64%)**; codec (enc 18 + dec 16) is CPU and fully hidden by the 3-thread pipeline. `depformer.sample` scales **dead-linear at 0.72 ms/slice** (1→16 slices), independent of weight-bank reuse ⇒ it is **sequential-launch/latency-bound** (16 passes of a tiny dim-1024 single-token transformer, ~370 kernel launches/frame), not compute- or bandwidth-bound. This is the #1 target.
- **Mic path now pipelined** (`main.py:run_mic`): was encode→LM→decode serial in one thread (~58 ms/frame); now 3 threads (encoder→LM→decoder) like the file path, so the live critical path is just the LM step (~24 ms on M4). Costs one frame (80 ms) of added output latency, no quality change. Main lever for fitting the iPhone 80 ms budget.
- **Depformer-only lower-bit quant** (`class_predicate`, main stays q4): **q3 is quality-safe** (silence-in rms≈0.000 peak≈0.012, text coherent → `translations/leon_depq_q3.wav`); **q2 breaks** (babble/clip, silence rms≈0.11). But quant gives **zero M4 speedup** (59→59 ms serial) — confirms the depformer is launch-bound, not bandwidth-bound: no weights-only trick fixes it on M4. q3 only trims iPhone-side bandwidth; the 16 sequential launches remain. **Only the architectural parallel-codebook head (5a) removes the sequential passes.**
- **Codec-fidelity gate** (`translations/leon_gate_cb{16,12,8,6,4}.wav`): same generated tokens decoded at fewer codebooks — graceful, monotonic degradation (mel-dist 0.022@12, 0.049@8, 0.105@4; no energy collapse). Listen to decide if a fewer-codebook 5a retrain is acceptable. NB: inference-time depformer truncation is **not** a faithful dep_q=8 preview — generated codebooks feed back into the main stream, so dropping them pushes the main transformer OOD.

## Benchmarking (`code/remote_dataset/`)
Score FR→EN translation quality against a dataset. `download_covost2.py` pulls `fixie-ai/covost2` `fr_en` test (Common Voice audio bundled, human EN refs) → wav + `manifest.csv`; `run_batch.py` translates a manifest with the q4 fast path **loading the LM once**; `evaluate_translation_text.py` scores BLEU/chrF/WER on the text sidecars. (`download_french_english_unprocessed.py` is an earlier, weaker dataset — proverbs, no benchmark; avoid for comparisons.) If `HF_HOME` points at a dead mount, `export HF_HOME="$(pwd)/.hf_cache"`.
- **Tail-flush fix (`infer_mlx_fast.run`):** Hibiki is *simultaneous* (~6 s lag), so when input ends the translation tail is unspoken. `run()` now feeds trailing silence (`tail_s`, default 8 s) to flush it, then **early-stops** once the model emits `PAD_STOP`≈1 s of pad tokens (sitting in silence longer makes it hallucinate/repeat). `run()` also gained `preloaded=` (skip reload) and `make_mimi()` (fresh codec state per file). Mic path unchanged.
- **Spurious cold-start lead-in fix (text temp):** a few short clips got a hallucinated opener before the real translation (`fr_0023`: "Are you there? We have tabled amendments…"). Per-frame probe (`scripts/exp_warmup_probe.py`) + seed/temp sweep (`scripts/exp_text_temp_bench.py`) show it's a **text-sampling artifact**, not warmup structure — emitted text feeds back autoregressively (`generate.py:77`), so one high-temp wrong sample at cold start commits the model to a bad opener it then has to recover from. Lowering **text** temp 0.8→**0.4** (audio stays 0.8) removed ~all genuine openers *and* raised BLEU (n=30 fixed-seed: 22.1→25.8; chrF 49.0→46.5). Greedy 0.0 over-collapses (BLEU 19.8). New default in `infer_mlx_fast.run(text_temp=0.4)` + `main.py` mic path.
- **q4 result (CoVoST 2 fr→en, n=30, M4 Pro):** BLEU **25.7**, chrF 49.4, WER 63%. Without the flush BLEU was ~9.6 (truncated tails). Below the paper's 30.6 / offline baselines (~36) as expected for a 4-bit *simultaneous* model on out-of-domain test data + small n. WER is a poor MT metric here (paraphrase counts as error) — read BLEU/chrF. Scale `--limit` to 100+ for low variance.

## FLEURS vi↔en dataset (`code/remote_dataset/fleurs_vi_en/`)
For future **Vietnamese support** work. `download_fleurs_vi_en.py` pulls `google/fleurs` `vi_vn`+`en_us`, joins rows on the shared FLoRes sentence `id` (n-way parallel), and writes per-split `{split}/{vi,en}/*.wav` (16 kHz mono) + `manifest.csv` (`id, vi_audio, en_audio, *_duration_s, text_vi, text_en`) — so each row has vi source audio + en target audio + both transcripts (usable for vi→en S2TT *and* S2ST). **Non-streaming** (caches parquet to `.hf_cache`, resumable); set `HF_HUB_DISABLE_XET=1 HF_HUB_DOWNLOAD_TIMEOUT=120` — the xethub CDN times out a lot. Totals: **train 1449 / val 149 / test 347 = 1945 pairs (vi 6.19h, en 5.51h)**. Small — eval/fine-tune scale, not from-scratch. `sphn.read(sr=24000)` resamples the 16 kHz wavs on load, so the q4 path runs them directly.
- **vi→en gap baseline (n=30 test, q4):** BLEU **0.26**, chrF 9.5, WER 113% — i.e. ~zero. Hibiki-Zero is **FR/ES/PT/DE→EN only**; fed Vietnamese it emits fluent-but-unrelated English (or empty/"Okay."). Confirms vi is unsupported and needs training, not just inference. Reuses `run_batch.py`+`evaluate_translation_text.py` via a `manifest_vien.csv` adapter (cols renamed to `audio_file`/`translation_en`).
- **Training scaffold/current run:** `code/finetune/` contains the PyTorch LoRA water-test path: `build_pairs.py` exports deterministic FLEURS JSONL/CSV pairs; `cache_codes.py` caches Mimi/text codes into `shard_*.pt` with paper-style coarse target delay (`--target-delay-ratio 0.5` default); `train_lora.py` freezes the PyTorch LM, inserts rank-16 LoRA in `LMModel.transformer` (`17.4M` params), optionally trains `LMModel.text_linear` via `--train-text-head` (adapter grows to ~221MB), trains CE through `LMModel.forward`, saves adapter `.safetensors` + optimizer checkpoints, supports resume, and logs loss + MPS memory; `eval_lora.py` loads LoRA-only and LoRA+text-head adapters and writes wav/txt + `predictions.csv`. Conda Python has `moshi==0.2.13` + `sphn==0.2.1` (downgrades `huggingface-hub`; `pip check` complains about `transformers`). Full FLEURS cache: 1449 train samples, 46 shards, 245,914 cached frames (~5.46h after delay padding; raw train source 4.44h). **Resume/memory fixes:** adapter weights copy into existing params (no `assign=True` after optimizer creation), sorted resume skips covered batches, condition tensors cache by batch size, and MPS sync+empty-cache defaults to every 10 steps. Old `vn_lora` resumed step400→500 stably but used the old objective and eval produced empty text. **Text objective fix:** old CE supervised text padding token `3` on ~84% of frames; now padding is masked while real tokens + EOS stay supervised and `text_tokens` is logged. Corrected transformer-only LoRA (`vn_lora_textmask`, step500) and text-only weighting probe (`vn_lora_textonly_lr5e4`, step200) still loop common tokens, so transformer-only capacity/feedback is insufficient. **Tiny broader-trainable overfit:** built `finetune/cache/seen_first3` from actual first sorted train rows (ids 213/211/245). Text-head-only overfit (`vn_lora_overfit_texthead_seen3_e200`, text loss ~0 by step200) still had generation drift because text was trained with teacher-forced target-audio context. Mixed text-head+audio overfit (`vn_lora_overfit_texthead_audio_seen3`, step450) drove text loss ~0.004 and audio loss ~1.64; greedy eval contains the full references but with repeated lead-ins (`don don...`, `when...`) before the correct sentence. Current status: mechanics are fixed and tiny overfit is partially successful; next target is reducing autoregressive lead-in/feedback mismatch before scaling beyond the 3-row cache. This is still a smoke-test scaffold; the Hibiki-Zero paper's Italian adaptation used ~850h supervised data and RL, so FLEURS alone is not enough for serious quality.

## Notes / gotchas
- Input must be FR/ES/PT/DE and **≤ `--gen-duration`** seconds (max 120). Every input is padded to gen-duration, so smaller = faster.
- Default dtype float16 (no MPS op errors); `--bf16` available.
- Performance: ~0.7× real-time on MPS (H100 does ~3× faster than real-time) — fine for offline, laggy for live.
- Verified working: bundled `samples/leon.wav` (~64 s FR Olympics) + `crepes.mp3` (~56 s FR recipe) → coherent EN text + 24 kHz audio (mono + stereo wav), on both the PyTorch/MPS path (`0_*` outputs) and the fixed MLX q4 path (`*_mlx_fixed.wav`, ~3× RT, no babble/clipping after the depformer-LayerNorm fix).
